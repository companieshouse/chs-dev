THROWAWAY PROTOTYPE · REVIEW · 5 NOVEMBER 2026

Useful context, readable service names, less code

Three alternatives to the earlier H command centre. All use the same fixture and current provider model: Service, Development and Mock. Evaluate the information hierarchy at 80 × 24 first, then try a larger terminal.

Keyboard: ↑↓ select, PgUp/PgDn page, / filter, Enter actions, Esc back. ←→ switch prototype variants. Browser buttons duplicate keys. Simulation controls are outside the TUI. The proposed app retains its existing global tab shortcuts.

What the existing prototypes get right

        

            H's strongest ideas are the grouped service list, visible version,
            selected-service context and environment change summary. These
            answer useful questions: what am I working on, what is running, and
            what will applying do? F/G also reduce the need to open a modal just
            to read a service.

Comparison with the current implementation

        

            The current TUI already has filtering, grouped rows, service
            actions, mock scenarios, versions, service logs, journey editing,
            runtime changes and auto-apply. The main opportunity is to make that
            information easier to see. The captured baseline uses the actual Ink
            ServicesScreen
            and TabBar, with
            synthetic data. It omits the outer app status/footer wiring; it is a
            screen capture, not a full live session. The app preview was blocked
            by the sandbox's Unix socket restriction.
        

        

            At 80 columns, the current optional columns reserve 54 cells before
            the service name and outer spacing. With both Start and Scenario
            present, the two accounts-filing services truncate to the same name.
            Development and always also touch because their column widths have
            no separating gap. Seven boxed tabs clip at that width. The new
            variants keep full names in a selection summary and show a short
            mode label in rows.
        

        

            J and K retain a compact version column: 12 cells in the full-width
            table, 8 in K's split table, with the full version in the selection
            summary/inspector. Start mode and scenario remain accessible through
            the existing editor. L displays desired configuration separately
            from observed runtime state. A stopped lazy service is labelled
            “Idle (lazy)” for readability; a real implementation must also
            consult intent, exclusions and user-stopped state before making that
            classification.

Keep the scope small

        

            Use one selected service name, one filter and one visible list.
            Share the current snapshot and action handlers; keep row layout and
            width rules in one place. Reuse
            ServiceModal,
            JourneysScreen
            and
            EnvironmentPanel. Avoid introducing a layout engine or a second settings editor.
            The prototype's compact tab line can be implemented with plain Ink
            Text; the full seven-tab layout must still be evaluated
            independently.
        

        

            The existing domain already exposes
            LiveState.changes,
            start/stop/recreate plans, exclusions and auto-apply. Feed the
            visible summary from that state and reuse
            the existing environment formatting. “Draft edits”, “saved changes awaiting apply” and “runtime
            failures” need separate labels. The earlier prototype changes
            observed status immediately when a provider is selected, then calls
            it pending; that would give misleading feedback in the real TUI.
        

        

            Recorded and remote providers, seed management, general undo, config
            provenance and exact CLI echoes need their own capability review.
            The current provider enum supports service, development and mock;
            disabling is a separate setting. Mock execution can also require
            infrastructure. A provider change is not proof that a service became
            healthy or that no containers are needed. These features are
            excluded from all three layout estimates.
        

        

            The simulation uses local fake actions and a reduced service editor.
            Production should reuse its existing complete editor, validation,
            revision checks, confirmations, auto-apply and error handling.
            Baseline captures are fixed to the original 12-service fixture;
            select a new variant for interactive and stress scenarios.
